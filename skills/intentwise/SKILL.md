# Intentwise

Preserve this sequence: **Intent -> Implications -> Consequential Decisions -> Autonomy -> Evidence**. This is intent and verification control, not planning or orchestration.

Whenever presenting an Intentwise-created file to the user, resolve and show its absolute filesystem path. When the interface supports Markdown file links, make the path clickable. Keep paths stored inside contracts and knowledge documents relative for portability.

When a request starts from an Azure DevOps (ADO) work item, use one direct Intentwise invocation by default: inspect the work item and repository, resolve consequential questions, create and semantically preflight the delivery contract, then stop at the approval boundary. Do not require the user to first generate an Intentwise prompt or handoff and submit that derived text in a second invocation. That two-step prompt-generation flow is optional audit/debug mode only when the user explicitly wants an inspectable intermediate artifact or a controlled workflow comparison.

Use authoring mode when creating or revising a contract. When the user asks only to review an existing draft, use review-only mode: do not edit the draft, reconstruct the semantic view from authoritative sources, complete the entire preflight even when structural validation fails, and return exactly one verdict from `READY`, `NEEDS REVISION`, or `BLOCKED`. Do not ask the user to choose a mode when the request already makes it clear.

Structural validity is not semantic readiness. Never return `READY` from structural validator success alone; `READY` requires the complete source-derived semantic preflight and no remaining material semantic finding.

Before explicit approval, authoring and review are read-only for the product.
Do not create, switch, or redirect work to another worktree; do not modify
source, tests, configuration, or product documentation; and do not move a
contract to `ready/`, `active/`, or `completed/`. The selected file under
`.intentwise/drafts/` and an explicitly requested audit artifact are the only
durable writes allowed. Before requesting approval, compare product-tree state
with the state observed at session start using the repository-designated
authority. If this session caused any other change, report an approval-boundary
violation and do not request approval. Never revert or overwrite unrelated user
changes.

## Shape the contract

1. Inspect repository and Intentwise sources proportionally before asking anything. Establish the exact authoritative request, the relevant current behavior and execution path, the observable gap, the confirmed participating scope, the proof target, and any material contradiction or unknown. Search `.intentwise/ready/`, `.intentwise/active/`, and `.intentwise/completed/` by task ID and affected behavior; approved and verified contracts remain product authority unless a current authoritative request explicitly supersedes them. Stop at evidence saturation, when further inspection is unlikely to change that core. Expand into adjacent components, related work items or history, external research, migrations, rollout, or broader architecture only when evidence reveals a material dependency, shared contract, cross-boundary behavior, security or data consequence, compatibility concern, conflicting authority, or important failure semantics. Possible scope is not required scope; do not inventory everything merely because it is available, and never use an arbitrary file or time limit to truncate material evidence. Infer what implementation sources establish without treating current code or tests as permission to change intended behavior. When an unresolved consequential decision depends on current platform behavior, domain practice, organizational precedent, or an unfamiliar integration, use available connected sources and authoritative primary sources following [evidence-backed discovery](references/questioning.md#evidence-backed-discovery); do not present model memory as researched fact or turn ordinary implementation choices into a market survey.
2. Restate the intended observable outcome and derive its important implications.
3. Identify only choices whose consequences cross the [decision frontier](references/decision-frontier.md). Do not surface uncertainty merely because implementation is difficult.
4. For each unresolved consequential choice, ask one outcome-focused question at a time. Recommend the best fit for the repository and user intent—not an abstract universal best practice—and state its evidence basis, applicability, and consequences. Follow [questioning guidance](references/questioning.md).
5. Stop questioning when remaining choices are local, reversible, conventional, or mechanical. A clear low-consequence task normally needs no questions. Use a tiny contract only when an acceptance condition, constraint, or decision is worth preserving; otherwise proceed directly.
6. For non-trivial work, read [delivery guidance](references/delivery-guidance.md) and the mandatory [draft-readiness preflight](references/draft-preflight.md). Before writing acceptance criteria or evidence plans, build its temporary source-derived semantic readiness view. Resolve applicable operational definitions, input and failure states, classification and reconciliation rules, unknown-value behavior, observed baselines versus lasting invariants, exact compatibility properties, provenance, scope ownership, and volatile execution context. Classify sources by authority: explicit current requirements and approved or verified decisions constrain product meaning; code and tests describe the present implementation unless an authoritative source makes them compatibility requirements. Do not treat a proposed draft or the reasoning that produced it as evidence. If a genuinely unresolved consequential blocker remains after applying the preflight's progress rules, ask one targeted question before drafting.
7. When the semantic view is ready, write the compact, OKF-compatible [delivery contract](references/contract-template.md) as `DRAFT` to its own `.intentwise/drafts/<contract-id>.md`. Prefer an existing issue or task ID plus a short slug; otherwise use a UTC timestamp, short slug, and six-character random suffix. Never overwrite an existing contract. Record outcomes, maintainability expectations, and constraints, never an implementation task list unless the user explicitly asks for one. Make the target concrete with the smallest useful diagram or before/after representation, observable interaction states, user-visible invariants, and one representative success scenario. Use Mermaid or plain text when a flow materially improves understanding; do not invent a flow for work that is clearer as a state table or before/after mapping. Label missing, uncertain, or intentionally out-of-scope behavior rather than implying completeness. Map material states and rules to acceptance criteria without duplicating an implementation plan. Use the preflight commitment-to-clause-to-assertion mapping so compact wording preserves every authoritative obligation and each has a concrete proof target. An anticipated change surface and delivery-strategy expectations are advisory; they may influence evidence without prescribing the harness's implementation order.
8. Before presentation, complete the preflight's final adversarial audit against the raw sources and temporary semantic view. Run the structural validator, but treat each structural error as a finding and continue the semantic audit unless the draft or authoritative sources are unreadable. Attack every criterion with a counterexample, check lifecycle-contract consistency and scope ownership, re-query any material managed branch, target, or worktree state through the repository-designated authority, and verify that every planned verification can reach its required evidence level. In authoring mode, automatically correct every source-resolved defect and revalidate; do not hand a repairable draft back to the user merely because an audit pass found it. In review-only mode, never edit unless the user asks; report all material findings, not only the first failure. Return `NEEDS REVISION`, not `BLOCKED`, when authoritative sources already establish the correction. Use `BLOCKED` only when an unresolved choice crosses the decision frontier, no authoritative source resolves it, and choosing a default would create material risk or costly reversal, or when missing context is required to determine what should be built. Local or reversible uncertainty remains delegated or explicit, and unavailable verification evidence later becomes `UNPROVEN`. Preflight never self-approves a contract and does not require another agent.
9. In authoring mode, present only a preflight-ready draft contract, its absolute path, and the compact readiness summary, then stop for review. In review-only mode, present the verdict, compact coverage, and actionable findings without rewriting the draft. Do not persist the semantic worksheet, critic notes, or a confidence score unless the user explicitly requests an audit artifact. Only explicit user acceptance authorizes approval; never self-approve or infer approval from having written, reviewing, or preflighting the contract. On acceptance, record `APPROVED`. If `Execution` is `DEFERRED`, move the contract to `.intentwise/ready/<contract-id>.md` and stop. If it is `CONTINUE`, move it to `.intentwise/active/<contract-id>.md` and proceed. Do not begin implementation before acceptance or while a contract remains under `drafts/` or `ready/`.

The human owns intended outcomes, external behavior, consequential trade-offs, architectural commitments, privacy/security choices, constraints, and acceptance criteria. The coding agent owns every implementation choice not constrained by the contract, including decomposition, ordinary APIs, file organization, refactoring mechanics, tools, tests, iteration, and debugging.

## Implement

Treat a user-approved contract as authoritative while independently inspecting the repository and choosing the implementation path. When the user explicitly starts a contract under `ready/`, change its execution disposition to `CONTINUE`, move it to `active/`, and proceed; this does not reopen the approved product decisions. Do not ask approval for delegated choices. Apply its [learning mode and delivery guidance](references/delivery-guidance.md) without turning learning checkpoints into approval gates. The anticipated change surface and implementation strategy may evolve without approval as local choices become clearer. Stop only if new information creates a consequential decision outside the approved contract; difficulty or ordinary implementation divergence alone is not a reason to stop.

Track the selected contract as it moves between lifecycle directories. Update only the contract this session created or was explicitly asked to resume; other files in `drafts/`, `ready/`, and `active/` belong to other work. If present, validate the selected file with `python3 <skill-directory>/scripts/validate_contract.py <contract-path>`. A successful structural check does not prove runtime behavior.

## Verify and close

Read [verification guidance](references/verification.md), then independently assess every acceptance criterion against its required evidence. Report exactly `PASS`, `FAIL`, or `UNPROVEN`; never accept an implementation claim as proof or silently lower the required evidence level. When evidence demonstrates `FAIL`, remediate the implementation and verify again unless doing so requires a new consequential decision or progress is genuinely blocked. Do not turn missing evidence into implementation churn: if required evidence cannot be obtained, report `UNPROVEN`.

Update the selected contract's status, actual change surface, observed evidence levels, and verification result. Before marking it `VERIFIED`, persist the compact [delivery retrospective](references/verification.md#delivery-retrospective) and follow [knowledge and asset guidance](references/knowledge-and-assets.md): promote durable current knowledge inside `.intentwise/knowledge/`, keep rich media in `.intentwise/assets/`, and record what was promoted. When all criteria pass, validate the completed record, set it to `VERIFIED`, and move that same file to `.intentwise/completed/<contract-id>.md`; the delivery is not closed while its verified contract remains active. Otherwise leave it active. Use the retrospective for the final report; do not narrate routine steps or hidden reasoning.
