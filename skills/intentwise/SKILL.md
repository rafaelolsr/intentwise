# Intentwise

Preserve this sequence: **Intent -> Implications -> Consequential Decisions -> Autonomy -> Evidence**. This is intent and verification control, not planning or orchestration.

Whenever presenting an Intentwise-created file to the user, resolve and show its absolute filesystem path. When the interface supports Markdown file links, make the path clickable. Keep paths stored inside contracts and knowledge documents relative for portability.

When a request starts from an Azure DevOps (ADO) work item, use one direct Intentwise invocation by default: inspect the work item and repository, resolve consequential questions, create and semantically preflight the delivery contract, then stop at the approval boundary. Do not require the user to first generate an Intentwise prompt or handoff and submit that derived text in a second invocation. That two-step prompt-generation flow is optional audit/debug mode only when the user explicitly wants an inspectable intermediate artifact or a controlled workflow comparison.

Use authoring mode when creating or revising a contract. When the user asks only to review an existing draft, use review-only mode: do not edit the draft, reconstruct the semantic view from authoritative sources, complete the entire preflight even when structural validation fails, and return exactly one verdict from `READY`, `NEEDS REVISION`, or `BLOCKED`. Do not ask the user to choose a mode when the request already makes it clear.

Structural validity is not semantic readiness. Never return `READY` from structural validator success alone; `READY` requires the complete source-derived semantic preflight and no remaining material semantic finding.

Before explicit approval, authoring and review are read-only for the product.
Do not create, switch, or redirect work to another worktree; do not modify
source, tests, configuration, or product documentation; and do not move a
contract to `ready/`, `active/`, or `completed/`. The selected file under
`.intentwise/drafts/` and an explicitly requested audit artifact are the only
durable writes allowed. Before requesting approval, compare product-tree state
with the state observed at session start using the repository-designated
authority. If this session caused any other change, report an approval-boundary
violation and do not request approval. Never revert or overwrite unrelated user
changes.

## Shape the contract

1. Inspect repository and Intentwise sources proportionally before asking anything. Establish the exact authoritative request, the relevant current behavior and execution path, the observable gap, the confirmed participating scope, the proof target, and any material contradiction or unknown. Search `.intentwise/ready/`, `.intentwise/active/`, and `.intentwise/completed/` by task ID and affected behavior; approved and verified contracts remain product authority unless a current authoritative request explicitly supersedes them. Stop at evidence saturation, when further inspection is unlikely to change that core. Expand into adjacent components, related work items or history, external research, migrations, rollout, or broader architecture only when evidence reveals a material dependency, shared contract, cross-boundary behavior, security or data consequence, compatibility concern, conflicting authority, or important failure semantics. Possible scope is not required scope; do not inventory everything merely because it is available, and never use an arbitrary file or time limit to truncate material evidence. Infer what implementation sources establish without treating current code or tests as permission to change intended behavior. When an unresolved consequential decision depends on current platform behavior, domain practice, organizational precedent, or an unfamiliar integration, use available connected sources and authoritative primary sources following [evidence-backed discovery](references/questioning.md#evidence-backed-discovery); do not present model memory as researched fact or turn ordinary implementation choices into a market survey.
2. Restate the intended observable outcome and derive its important implications.
3. Identify unresolved user-owned choices whose consequences cross the [decision frontier](references/decision-frontier.md). A meaningful product choice deserves a question even when implementation is easily reversible. Resolve factual questions from the codebase; do not surface uncertainty merely because implementation is difficult.
4. Ask in rounds: group independent outcome-focused questions whose prerequisites are settled, number them, and give each a recommendation grounded in repository evidence and user intent, with its consequence. Wait for answers, then recompute the next round; defer dependent choices until their parent is answered. Recommendations and silence are not decisions. Follow [questioning guidance](references/questioning.md).
5. Stop questioning when remaining choices are delegated implementation details or already resolved by authority. A clear low-consequence task (a rename, a copy fix, a one-flag addition with an obvious contract) needs no questions, no contract and no preflight: state the intended outcome in a sentence, implement, and verify with the project's existing checks. Use a tiny contract only when an acceptance condition, constraint, or decision is worth preserving; otherwise proceed directly.
6. For non-trivial work, read [delivery guidance](references/delivery-guidance.md) and the mandatory [draft-readiness preflight](references/draft-preflight.md). Build a compact source-derived readiness view covering the material outcomes, states, constraints, and proof targets for this task. The codebase is the source of truth for current behavior and feasibility; explicit current requirements and approved decisions establish intended behavior. Neither a proposed draft nor its reasoning is evidence. If unresolved user-owned choices remain, ask the next question round before drafting.
7. Write the [delivery contract](references/contract-template.md) as `DRAFT` under `.intentwise/drafts/<contract-id>.md`, using `intentwise/v0.4` with `format: compact` by default. Prefer an issue ID plus slug; otherwise use a UTC timestamp, slug and six-character random suffix. Never overwrite another contract. Record material outcomes, protected constraints and criteria once; do not copy the same facts into multiple sections or turn examples and forecasts into obligations. Add a diagram, state view or detailed decision only when it materially helps approval; use the full format when separate views are useful or requested. Preserve the source commitment-to-criterion-to-assertion mapping. Every criterion must trace to the user's request, an applicable approved decision, or a protected constraint. A criterion the agent proposes to protect against a concrete failure the sources imply (for example a missing-input case) is allowed but must be labelled `Agent-proposed:` in its `Sources` field and surfaced at approval for the user to keep or drop; never present it as the user's requirement, and drop any obligation that is only a preference or generic best practice. Audit unrequested exclusions as well as added requirements: current implementation limitations cannot silently narrow the desired outcome. Resolve source-established gaps without another question; surface a genuinely consequential scope change prominently before approval.
8. Before presentation, complete the preflight's final adversarial audit against the raw sources and temporary semantic view. Run the structural validator, but treat each structural error as a finding and continue the semantic audit unless the draft or authoritative sources are unreadable. Attack every criterion with a materially wrong counterexample, check lifecycle-contract consistency and scope ownership, re-query any material managed branch, target, or worktree state through the repository-designated authority, and verify that planned checks can reach the required evidence. Remove unauthorized promises rather than tightening everything into exact guarantees. In authoring mode, correct source-resolved defects and revalidate; in review-only mode, report all material findings without editing. Return `NEEDS REVISION`, not `BLOCKED`, when authoritative sources establish the correction. Use `BLOCKED` when an unresolved user-owned choice materially changes the outcome, risk, compatibility, or commitment, or missing context prevents determining what should be built. Implementation uncertainty remains delegated or explicit; unavailable observed evidence later becomes `UNPROVEN`. Preflight never self-approves a contract and does not require another agent.
9. Present the preflight-ready draft, absolute path and brief readiness result, then stop for review. For review-only work, present the verdict and material findings without rewriting. Coverage counts are optional; do not persist worksheets, critic notes or confidence scores unless requested. Only explicit user acceptance authorizes approval; never infer it from drafting or preflight. Record `APPROVED` on acceptance. With `Execution: DEFERRED`, move to `.intentwise/ready/<contract-id>.md` and stop; with `CONTINUE`, move to `.intentwise/active/<contract-id>.md` and proceed. Do not implement while approval remains open or the contract remains under `drafts/` or `ready/`.

The human owns intended outcomes, external behavior, consequential trade-offs, architectural commitments, privacy/security choices, constraints, and acceptance criteria. The coding agent owns every implementation choice not constrained by the contract, including decomposition, ordinary APIs, file organization, refactoring mechanics, tools, tests, iteration, and debugging.

## Implement

Treat a user-approved contract as authoritative while independently inspecting the repository and choosing the implementation path. When the user explicitly starts a contract under `ready/`, change its execution disposition to `CONTINUE`, move it to `active/`, and proceed; this does not reopen the approved product decisions. Do not ask approval for delegated choices. Apply its [learning mode and delivery guidance](references/delivery-guidance.md) without turning learning checkpoints into approval gates. The anticipated change surface and implementation strategy may evolve without approval as local choices become clearer. Stop only if new information creates a consequential decision outside the approved contract; difficulty or ordinary implementation divergence alone is not a reason to stop.

Allow variation within the agreed outcomes and tolerances. File layout, helpers, presentation details, fixtures, and verification tools may evolve unless explicitly protected. Replace a planned check with equivalent or stronger evidence of the same property and boundary; record meaningful substitutions. A change to the promised outcome, protected constraint, tolerance, or minimum evidence requires a focused amendment with the user. Pause only work that depends on that choice. See [verification guidance](references/verification.md#variation-and-amendments).

Track the selected contract as it moves between lifecycle directories. Update only the contract this session created or was explicitly asked to resume; other files in `drafts/`, `ready/`, and `active/` belong to other work. If present, validate the selected file with `python3 <skill-directory>/scripts/validate_contract.py <contract-path>`. A successful structural check does not prove runtime behavior.

## Verify and close

Read [verification guidance](references/verification.md), then independently assess every acceptance criterion against its required evidence. Report exactly `PASS`, `FAIL`, or `UNPROVEN`; never accept an implementation claim as proof or silently lower the required evidence level. When evidence demonstrates `FAIL`, remediate the implementation and verify again unless doing so requires a new consequential decision or progress is genuinely blocked. Do not turn missing evidence into implementation churn: if required evidence cannot be obtained, report `UNPROVEN`.

Update the selected contract's status, actual change surface, observed evidence and results. Before `VERIFIED`, write the brief [delivery retrospective](references/verification.md#delivery-retrospective). Follow [knowledge guidance](references/knowledge-and-assets.md) only when there is durable knowledge to promote; ordinary task-local facts stay in the contract. When all criteria pass, set `VERIFIED`, move the same file to `.intentwise/completed/<contract-id>.md`, then validate it there (the validator rejects `VERIFIED` outside `completed/`); otherwise leave it active with honest results. Report the delivered outcome and material limitations without repeating the full record.
