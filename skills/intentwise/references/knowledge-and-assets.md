# Knowledge and Assets

## Self-contained layout

Keep everything Intentwise creates under the project-local `.intentwise/` directory:

```text
.intentwise/
├── index.md
├── drafts/
├── ready/
├── active/
├── completed/
├── knowledge/
│   ├── index.md
│   ├── architecture/
│   ├── decisions/
│   ├── external/
│   └── operations/
└── assets/
    ├── diagrams/
    ├── images/
    └── visualizations/
```

Do not create root-level documentation folders. If the repository already has authoritative documentation elsewhere, update it only when repository instructions or the approved contract explicitly require that.

## OKF compatibility

All persistent Markdown generated by Intentwise, except reserved `index.md` and `log.md` files, must begin with YAML frontmatter containing a non-empty `type`. Use:

- `Intentwise Delivery Contract` for active and completed contracts.
- `Architecture` for current system structure and flows.
- `Decision` for durable architectural or product decisions.
- `External System` for integrations, configuration shape, ownership, privacy, and failure behavior.
- `Operations Playbook` for current operational procedures.

Prefer `title`, `description`, `tags`, and an ISO 8601 UTC `timestamp`. Use `resource` when a knowledge document describes a canonical external asset. Keep Intentwise's stricter contract schema in the Markdown body; OKF metadata does not replace lifecycle or evidence validation. Put externally sourced claims under a `# Citations` heading.

Keep the root index stable and descriptive. Do not make concurrent sessions rewrite a shared contract registry; lifecycle directories already express state. A knowledge index may list current canonical concepts, but shared knowledge is concurrency-safe only by convention: re-read the index and target immediately before editing, reconcile changes made since initial inspection, and never overwrite a version the session did not inspect. If a safe reconciliation is impossible, stop at that consequential conflict instead of claiming promotion succeeded.

Use this compact shape for a knowledge concept, omitting sections that do not apply:

```markdown
---
type: Architecture | Decision | External System | Operations Playbook
title: <human-readable name>
description: <one-sentence current meaning>
resource: <canonical URI when applicable>
tags: [<short tags>]
timestamp: <ISO 8601 UTC>
---

# Current State

<what is true now>

# How It Works

<important relationships, data or control flow, and operational behavior>

# Limitations

<known constraints and residual risks>

# Provenance

- [<delivery contract>](../../completed/<contract-id>.md)

# Citations

1. [<source>](<URL or bundle-relative path>)
```

## Promote durable knowledge

Completed contracts are immutable provenance: what was intended, decided, implemented, and verified at delivery time. Knowledge documents are mutable descriptions of what is true now.

Before verification, classify what the delivery taught:

- **Task-local:** retain only in the completed contract.
- **Durable architecture:** create or update `.intentwise/knowledge/architecture/`.
- **Durable decision:** create or update `.intentwise/knowledge/decisions/`.
- **External integration:** create or update `.intentwise/knowledge/external/`.
- **Operational behavior:** create or update `.intentwise/knowledge/operations/`.

Link knowledge documents to their completed-contract provenance and link the contract's `Knowledge Promotion` section back to every concept changed. Never store secrets, credentials, tokens, customer data, or unverified transient state.

## Keep rich assets separate

Store SVGs, images, HTML visualizations, and other enduring teaching media under `.intentwise/assets/`, never inside `knowledge/`. Reference each asset from at least one contract or knowledge document. Use deterministic, project-relative names; replace obsolete generated assets when their canonical concept changes. Do not retain temporary screenshots, recordings, build output, or duplicated evidence without enduring explanatory value.

Use plain Markdown, ASCII, or Mermaid when the host can produce no richer artifact. SVG, image, and interactive HTML generation is capability-dependent and must never be represented as guaranteed by Intentwise itself.

Reference a rich asset from its knowledge concept with an ordinary relative Markdown link:

```markdown
![Telemetry flow](../../assets/diagrams/telemetry-flow.svg)

[Explore the telemetry architecture](../../assets/visualizations/telemetry-architecture.html)
```
